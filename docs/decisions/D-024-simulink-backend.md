# D-024 — MATLAB/Simulink as a third simulation backend

**Date:** 2026-08-18 · **Status:** accepted, **validated** · **Type:**
architecture / reproduction

## Context

The project already has two backends that solve the same equations: the Python
scientific core (`src/cacc`, D-002) and the distributed ROS 2 stack
(`ros2_ws`, D-011). The user asked for a **Simulink** simulation that does
"everything the base paper did" — i.e. a block-diagram model of the Ma-2025
CTHP platoon that regenerates the paper's Figs. 4–15 and Tables I–II.

Three things made this worth doing beyond satisfying the request:

1. **Independent reproduction.** Two implementations written from the paper by
   *different routes* — hand-written RK4 on a state vector vs. a vectorised
   block diagram integrated by Simulink's `ode4` — agreeing to 1e-4 is far
   stronger evidence than either alone. It closes the third leg of the
   cross-backend matrix (V-03, V-05 §5).
2. **Audience.** A control-systems examiner reads a block diagram faster than
   they read `platoon.py`. The `.slx` makes the control law, the spacing
   policy, the channel and the one-vehicle-look-ahead topology visible at a
   glance.
3. **Cost.** MATLAB R2026a with Simulink is already installed and works
   headless (`matlab -batch`), so the build is scriptable and CI-able. No new
   dependency.

## Decision

Add `matlab/` as a third backend with four properties:

1. **The `.m` builder is the source of truth; the `.slx` is a build artefact.**
   `models/build_cacc_model.m` constructs the model programmatically
   (`new_system`/`add_block`/`add_line`) and saves it. The binary `.slx` is
   regenerated by deleting it and re-running. This keeps the model reviewable
   and diffable in git — a binary model file that nobody can review is a
   liability in a project whose whole thesis is auditable virtual validation.

2. **Vector signals of width N, not N copies of a subsystem.**

3. **Three channel modes selected by two parameter values, not by a switch.**

4. **Parameters passed via `Simulink.SimulationInput`, never the base
   workspace.** Runs are side-effect free, replayable and parallelisable.

## Options considered

### A. Vectorised platoon (chosen)

States `x, v, a` are width-`N` signals; the entire inter-vehicle coupling is
one constant matrix `PredSel = [I_N  0]` applied to `[leader ; followers]`.

* **Buys:** `N` is a parameter, not a diagram edit. Heterogeneous parasitic
  lags (Case 5, Table II) are a vector `tau_vec` with zero diagram change. The
  diagram is ~30 blocks total. The one-vehicle look-ahead information topology
  is a *single visible block* — pedagogically the best possible rendering.
* **Costs:** individual vehicle signals must be indexed out for plotting
  (trivial in the post-processing scripts). Per-vehicle heterogeneity beyond
  `τ` (e.g. different gains) would need extra vectors.
* **Kill condition:** none encountered.

### B. `N` replicated masked subsystems, wired predecessor-to-follower

* **Would buy:** the most literal rendering of "a platoon"; each vehicle is a
  block you can open.
* **Costs:** 12 vehicles × ~10 blocks = a 120-block diagram that no one will
  read; changing `N` means regenerating the whole layout; Case 5 needs a
  per-instance mask parameter. Line routing between 12 subsystems is where
  programmatic model building goes wrong.
* **Kill reason:** the readability argument that motivates a Simulink backend
  at all is *lost* at 12 vehicles, which is exactly the paper's `N`.

### C. `For Each` subsystem over a vectorised signal

* **Would buy:** per-vehicle partitioned parameters natively (Case 5 for free),
  with one visible "vehicle" block.
* **Costs:** the predecessor coupling is *not* per-element — vehicle `i` needs
  vehicle `i−1`'s state — so the shift must still be formed outside the
  `For Each`, which is the only non-trivial piece anyway. Adds a block type
  whose semantics need explaining without removing any work.
* **Kill reason:** all of option A's complexity, plus a construct that obscures
  rather than clarifies.

### D. A single MATLAB Function block containing the whole ODE

* **Would buy:** the shortest implementation; direct transliteration of the
  Python `_deriv`.
* **Costs:** it is *not a block diagram* — the deliverable becomes "MATLAB code
  inside a box", which reproduces the Python core's weakness (nothing visible)
  while adding Simulink's overhead. Also blocks code generation without extra
  work.
* **Kill reason:** defeats the purpose (reason 2 in Context).

### E. Noise mode by a `Switch` block

* **Would buy:** the mode visible in the diagram.
* **Costs:** three signal paths, two of them dead in any given run; the diagram
  now shows machinery that is not part of the model being certified.
* **Kill reason:** the chosen alternative — setting `noise_K = 0` and
  `noise_bias = E[w]` — makes *the same diagram* realise all three modes.
  Strictly simpler, and the mode is recorded in `P.noise_mode` where the
  results carry it.

### F. Variable-step solver (`ode45`)

* **Would buy:** automatic accuracy control.
* **Costs:** the channel is a piecewise-constant discrete signal with a 10 ms
  hold; a variable-step solver takes a zero-crossing/step-rejection hit at
  every hold boundary — 20 000 of them per 200 s run.
* **Kill reason:** fixed-step `ode4` at 1 ms divides `ts_noise` exactly, matches
  the Python core's integrator family, and runs a 200 s / 12-vehicle case in
  ~1.5 s. Accuracy was verified by agreement with the Python core to 1e-4.

## Consequences

* **Positive.** Ma-2025 is now reproduced by two independent numerical routes
  (V-05 §4.1: 4-decimal agreement on all three cases). Every closed form of
  Theorems 1–2 is checked numerically against a *different* method than the one
  used to state it (grid search vs closed form; polynomial residual vs symbolic
  expansion; `roots()` vs Routh–Hurwitz) — `theorem_checks.m`.
* **Positive.** Two findings the Python work had not made explicit:
  * the paper's time-domain figures are the **equivalent deterministic system**
    (eq. 13 / Remark 5), not stochastic realisations — realisation jitter is
    ≈2 % against a ≈0.35 % effect (V-05 §3);
  * a **counterexample** to the necessity of conditions (28a)/(28b), found by
    search rather than asserted (`theorem_checks.m` block F), which supports
    T-07 and D-017's fixed-gain-wall reasoning.
* **Negative / accepted.** A third backend is a third thing to keep green. It
  is mitigated by the model being generated from a reviewable `.m` file and by
  the whole reproduction being one command (`run_all`).
* **Open.** Case 3 / Fig. 12 disagrees by 15 % (V-05 §4). Characterised, not
  resolved; not blocking, since Case 3's qualitative claims all reproduce.
* **Not adopted.** The Simulink backend does **not** implement the project's
  own extensions (delay budget D-008, QoS adaptation D-016/17, spoof gate
  D-022, chance-constrained certificate D-023). Those live in the Python core,
  which remains the research vehicle. Simulink's job is faithful reproduction
  of the base paper and independent cross-validation — scope deliberately
  bounded.

## Invariants this decision adds

1. `matlab/run_all.m` completes and its summary table shows 0.00 % on all four
   theory rows.
2. `matlab/tests/crosscheck_python.py` agreement with the Python core stays
   within 1e-3 on `max|δ_i|` for Cases 1–3 under the ideal channel.
3. `models/cacc_platoon.slx` is never hand-edited — changes go through
   `build_cacc_model.m`, and the `.slx` is regenerated.
4. `matlab/slprj/` and `*.slxc` are gitignored (Simulink build cache).
